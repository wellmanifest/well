# Wellm governance profile v1

`wellm-governance-profile@1` makes Wellm an authoring and normalization layer
without breaking existing governance consumers that still require JSON and JSON
Schema Draft 2020-12.

The profile separates four concerns:

```text
Wellm authoring source
        ↓ parse + source map
Core data / policy IR
        ↓ type/schema/policy validation
canonical generated artifact
        ↓ exact-byte hash + semantic hash
existing governance scripts, CI, lock and external evidence
```

## What remains JSON

The first profile deliberately keeps these artifacts in their established
interchange formats:

- `*.schema.json` remains JSON Schema Draft 2020-12;
- generated `manifest.lock.json` remains deterministic JSON;
- external approval evidence remains JSON;
- public adoption artifacts remain JSON where existing Bash, Python, Node and CI
  consumers read them directly.

Wellm sources can generate instance data such as the manifest, ticket intent,
diagnostic catalogue and stack profiles. Removing public JSON is not required.

## Named formatting profiles

| Profile | Purpose | Ordering | Presentation loss |
|---|---|---|---|
| `wellm-typed@1` | authoring with type hints | source/canonical formatter | comments may be normalized |
| `json-data@1` | readable JSON | input object order | whitespace normalized |
| `repo-json@1` | Git, CI and lock inputs | schema properties, then lexical dynamic keys | whitespace normalized |
| `wire-json@1` | transport and semantic hashing | recursive lexical keys, compact | presentation removed |
| `yaml-json@1` | human-readable YAML | schema/lexical order | comments, anchors and tags removed |
| `hcl-static@1` | static HCL-compatible data | data model order | expression semantics unavailable |
| `typescript-data@1` | browser/Node data module | schema/lexical order | arbitrary TypeScript forbidden |
| `policy-md@1` | Markdown policy blocks | document order | compatibility fences normalized |

List profiles:

```bash
wellm profiles
```

## Deterministic repository JSON

`repo-json@1` fixes:

- UTF-8;
- LF newlines;
- two-space indentation;
- one final newline;
- no duplicate keys;
- no NaN or Infinity;
- NFC Unicode normalization;
- schema property order for declared records;
- lexical order for dynamic maps;
- original array order.

Format a document:

```bash
wellm fmt governance/manifest.wm \
  --profile repo-json@1 \
  --schema governance/manifest.schema.json \
  --output governance/manifest.default.json
```

Check without writing:

```bash
wellm fmt governance/manifest.wm \
  --profile repo-json@1 \
  --schema governance/manifest.schema.json \
  --output governance/manifest.default.json \
  --check
```

## Artifact and semantic hashes

Every generated artifact can have two independent hashes:

```text
artifactSha256 = SHA-256 of exact generated bytes
semanticSha256 = SHA-256 of compact normalized JSON meaning
```

A formatting-only change can alter `artifactSha256` while preserving
`semanticSha256`. A data change alters the semantic hash.

The generated sidecar has the form:

```json
{
  "schema": "wellm.artifact-metadata/v1",
  "source": "manifest.wm",
  "target": "generated/manifest.default.json",
  "sourceDialect": "typed@1",
  "targetProfile": "repo-json@1",
  "schemaRef": "fixtures/manifest.schema.json",
  "generator": {"name": "wellm", "version": "0.2.0rc3"},
  "sourceSha256": "sha256:...",
  "schemaSha256": "sha256:...",
  "semanticSha256": "sha256:...",
  "artifactSha256": "sha256:..."
}
```

The sidecar is not inserted into the governed document. This preserves schemas
that use `additionalProperties: false`.

## Source maps

For JSON, YAML, HCL-shaped and typed sources, Wellm records JSON Pointer to
source ranges:

```json
{
  "schema": "wellm.source-map/v1",
  "source": "intent.wm",
  "generated": "generated/intent.json",
  "mappings": {
    "/ticket": {
      "sourceLine": 3,
      "sourceColumn": 1,
      "endLine": 3,
      "endColumn": 7
    }
  }
}
```

Schema diagnostics use the closest mapped pointer. A failing `/allowedPaths/0`
therefore points back to the authored `.wm` line rather than only the generated
JSON path.

## Governance project file

Example:

```yaml
schema: wellm.governance-project/v1
root: .

sources:
  - id: governance-manifest
    source: manifest.wm
    target: generated/manifest.default.json
    schema: fixtures/manifest.schema.json
    sourceDialect: typed
    profile: repo-json@1
    metadata: true
    sourceMap: true

policies:
  - source: fixtures/CONTRIBUTING.md
    irTarget: generated/CONTRIBUTING.policy.ir.json
    canonicalFence: wellm-policy
    rewriteFences: false
    undeclaredStates: warning
```

Build:

```bash
wellm governance build examples/governance/wellm.project.yaml
```

CI check:

```bash
wellm governance build examples/governance/wellm.project.yaml --check
```

`--check` fails for:

- missing generated files;
- byte drift;
- stale metadata or source-map sidecars;
- JSON Schema errors;
- policy lint errors;
- missing policy IR.

No source or target outside the declared project root is written.

## Policy Markdown

Canonical fenced block names are:

```text
dsl
policy
wellm-policy
```

A `bash`, `sh` or `shell` block is imported only when its first meaningful line
is unambiguously policy-shaped, such as `RULE`, `STATE` or `TRANSITION`. This
produces `WM-POLICY-101`.

Import:

```bash
wellm policy import CONTRIBUTING.md \
  --output .wellm/CONTRIBUTING.policy.ir.json
```

Lint:

```bash
wellm policy lint CONTRIBUTING.md
```

Rewrite only policy-shaped compatibility fences:

```bash
wellm policy fmt CONTRIBUTING.md \
  --rewrite-fences \
  --target-fence wellm-policy
```

Ordinary shell snippets are never rewritten.

Policy lint currently checks:

- duplicate stable rule identifiers;
- duplicate state declarations;
- undeclared transition sources;
- undeclared transition targets;
- undeclared `NEXT` states.

It does not guess whether a ticket status and a workflow state with similar
names are intended to be interchangeable.

## Semantic diff

Compare any two supported data dialects:

```bash
wellm semantic-diff \
  tests/fixtures/governance-current/manifest.default.json \
  tests/fixtures/governance-legacy/manifest.default.json
```

Machine-readable output:

```bash
wellm semantic-diff left.json right.yaml --format json
```

Changes are classified as:

```text
BREAKING      removed property/value or changed type
NON_BREAKING  added property/value
CHANGED       scalar replacement or list reordering
INFO          reserved for explanatory entries
```

The classifier is structural. It does not replace domain-specific release
policy or JSON Schema compatibility analysis.

## Round-trip report

```bash
wellm roundtrip governance/manifest.default.json \
  --via yaml,typescript,json \
  --schema governance/manifest.schema.json \
  --output .wellm/roundtrip.json
```

The report records each dialect, semantic hash, schema diagnostics and whether
the representation remained semantically equivalent. It distinguishes:

```text
LOSSLESS
NORMALIZED
LOSSY
UNSUPPORTED
```

A data projection can be semantically equivalent while losing comments,
spacing and inline type spelling. Full policy and API definitions require the
IR projection.

## Remote formatting service

HTTP:

```http
POST /v1/format
Content-Type: application/json

{
  "value": {"b": 2, "a": 1},
  "profile": "wire-json@1"
}
```

Response:

```json
{
  "profile": "wire-json@1",
  "semanticSha256": "sha256:43258cff...",
  "output": "{\"a\":1,\"b\":2}\n"
}
```

Semantic comparison:

```http
POST /v1/semantic-diff

{
  "left": {"a": 1},
  "right": {"a": 2}
}
```

The same operations are exposed over WebSocket (`format`, `semantic-diff`) and
registered URI Processes:

```text
wellmanifest://runtime/format/execute
wellmanifest://runtime/semantic-diff/query
```

Remote execution still requires a matching Contract AQL scope.

## JavaScript parity

The SDK exports:

```js
import {
  canonicalJson,
  canonicalizeData,
  semanticDigest,
  WellManifestClient,
} from "@wellmanifest/wellm-sdk";

const digest = await semanticDigest({b: 2, a: 1});
const response = await client.format(
  {b: 2, a: 1},
  {profile: "repo-json@1"},
);
```

Python and JavaScript use the same recursive lexical key ordering, compact JSON
and SHA-256 rule for JSON-compatible values.

## Included regression fixtures

`tests/fixtures/governance-current/` contains the supplied current governance
contract, including conditional approval evidence, GitHub App review support,
current diagnostics and the long procedural policy document.

`tests/fixtures/governance-legacy/` keeps the supplied older variant. The
semantic-diff tests intentionally report the differences; Wellm does not merge
or reconcile them silently.
